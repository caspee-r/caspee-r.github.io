The almighty cpu needs to talk to other devices, for instance the keyboard. in order for the cpu to get the keyboard input he has 2 choices:

1.  check repeatedly if there is any keyboard input (polling).
2.  fuck it i'm the almighty cpu, the keyboard will tell me if it have something for me (interrupts).

Let me give a quick analogy: imagine you are waiting for someone to send a message, probably you keep checking the notifications over and over again, until he sends a message. you message him back then do the same thing again and again. in contrast the cpu has more important things to do instead of **waiting** 'someone' (peripheral) to sends him anything, he is not a simp. instead the device notify (interrupt) the cpu to handle an important event.


# The Idea Behind Interrupts

The idea is very simple, instead of the cpu spending time checking for all devices events every time, we use a mechanism for the devices to notify the cpu when there is an event, which f a device event is an abstract term which can mean many things depending on the device (keyboard, mouse, network card) and the type of interrupt for example a network card can send :

-   interrupt for receiving packets
-   interrupt for transmitting packets
-   interrupt for hardware error


# Two Classes of Hardware Events

we need to distinguish between different hardware events based on their priority to the system, however, we can classify them into the following 2 classes:


## Normal Device Events

Usually generated by peripherals, and they are not critical to the system state i.e the cpu can choose to ignore them.


## Critical Hardware Events

An external event that indicates a condition requiring immediate attention from the processor, because continuing normal execution without responding to it may **compromise** the system's correctness, integrity, or operation.


# The anatomy of interrupts in Intel 8086 CPU

![img](/public/interrupts.png)

The old 8086 cpu package has 40-pin *DIP*, two interrupt-request inputs, NMI and INTR, and one interrupt-acknowledge output, INTA:

-   NMI pin 17 (input)
-   INTR pin 18 (input)
-   INTA pin 24 (output)


## interrupt request pin (INTR)

This pin is used for normal device events, when a device needs to send an interrupt, it needs to **assert** this pin signaling for an **interrupt request**, however, The CPU has only one INTR input for maskable interrupts, so a separate controller (PIC) is needed to accept interrupt requests from multiple devices and determine which request should be presented to the CPU.


## programmable interrupt controller (**8259 PIC**)

> quick note: Today, PIC is almost replaced by APIC which stands for **advanced programmable interrupt controller**.

The 8259 PIC has 8 **IRQ** (interrupt request) lines, IRQ0 to IRQ7 i.e 8 peripherals to connect to it. the PIC can be configured to forward or mask a device IRQ, and manage interrupts, this is why it's a *controller*. in order to route devices interrupts it must be wired to the cpu INTR pin. ![img](/public/pic.jpeg)


## Non Mask-able Interrupts (NMI)

This pin is used for the **Critical Hardware Events**. a component can send interrupts to the NMI if the internal architecture route it. for example a system can route a specific peripheral events to NMI. The rest of this article will focus on maskable hardware interrupts through INTR.


# Interrupt Request and Interrupt Acknowledgment

When a peripheral signal the PIC for an interrupt, the PIC **determines** that this interrupt should be **serviced** so it **asserts** the INTR pin. when the 8086 finishes the current instruction it will check the the **FLAGS** register specifically the **interrupt flag** (**IF)** this flag is used to enable/disable interrupts, if it's on i.e IF = 1, the cpu accepts the interrupt and asserts the INTA pin to send the interrupt acknowledgment i.e "i accept your interrupt request , give me the **interrupt vector** ". then the device fulfills the cpu request and puts the appropriate interrupt vector in the data bus.


# We have Got the Interrupt Vector, Now What ?

After a **successful** interrupt the cpu needs to handle it i.e execute code specific to handle this interrupt. but how does the 8086 cpu finds this code, it uses a lookup table i.e Interrupt Vector Table (IVT). IVT is a table of functions pointers or more accurately pointers to **interrupt handlers**, sometimes it's called **ISR** i.e interrupt service routine. The 8086 uses the interrupt vector to index the IVT and jumps to the interrupt handler execute it then jumps back to continue it's execution. Note that all critical hardware events has a fixed interrupt vector, for the 8086 NMI is associated with interrupt type 2..


# Outro

Instead of wasting CPU cycles constantly asking every device, **“Do you have something for me yet?”**, the hardware can raise an interrupt and let the CPU know when something actually needs its attention.

On the 8086, that journey looks roughly like this:

**Device → PIC → INTR → INTA → Interrupt Type → IVT → ISR**

We’ve only scratched the surface, though. There’s still plenty to uncover: how the PIC prioritizes multiple requests, how interrupt masking works, what exactly happens to the CPU's registers during an interrupt, and how all of this evolved into the interrupt architecture used by modern x86 systems.

But for now, remember the core idea: **The CPU doesn't need to keep asking. The hardware can knock on the door.**
